О плане
Три месяца, три крупных релиза, одна сквозная линия: каждый день встраивается в проект, ничего «в стол».
Что такое MiniNAS. Это персональное облачное хранилище: системная служба, которая делает из свободного места на диске том, расшаривает его по SMB с реальными правами, управляется через веб-панель (диски, шары, пользователи, мониторинг SMART, журнал, задачи), а также отдаёт файлы через браузер — листинг, скачивание, загрузка. К панели можно подключиться из любой точки мира по HTTPS с двухфакторной аутентификацией: сценарий «в кафе с телефона открыть свой домашний NAS и скачать файл» — целевой. Тот же продукт работает на Linux (LVM + Samba), ядро при этом не меняется ни на строчку — это доказательство архитектуры на интерфейсах бэкендов.
Структура трёх месяцев:
•	Месяц 1 (дни 1–30): фундамент → веб-слой → Windows-ядро → служба. Релиз v0.5.0.
•	Месяц 2 (дни 31–60): «взрослая» системная часть: прямой WinAPI (тома, ACL), MSI-установщик (WiX), полноценный tray, квоты, подпись бинарника; внешний контур: TLS + 2FA (день 47), security-аудит под интернет (день 52). Релиз v0.8.0.
•	Месяц 3 (дни 61–90): Linux-бэкенд, полировка, v1.0.0; веб-файловый менеджер «Файлы» + внешние сценарии доступа (дни 82–88), релиз v1.1.0; статья-кейс, портфель, собеседования.
Темп: месяц 1 — 8+ ч/день (дни 7, 14, 21, 28 — облегчённые); месяцы 2–3 — 6–8 ч/день. Если времени меньше — план растягивается пропорционально, структура не меняется.
Правило «минимального скоупа»: у каждого дня есть ядро (то, без чего день не засчитан) и расширения. Если к вечеру ядро не сделано — делаешь ТОЛЬКО ядро, расширения переносятся в BACKLOG.md. Лучше 30 дней живого проекта, чем 30 дней идеального плана.
Формат каждого дня
День расписан в едином формате: Цель → Теория → Шаги → Камни → Результат.
•	Цель — зачем день существует, одной фразой.
•	Теория — что прочитать/посмотреть ДО практики (30% времени). Учиться на шаг впереди задачи: теория всегда привязана к сегодняшнему коду, ничего «на будущее».
•	Шаги — конкретные действия по порядку, с ориентировочным временем (70% времени — руки в коде).
•	Камни — типовые грабли дня. Каждую надо воспроизвести руками хотя бы раз (сломать и починить): пережитое не забывается, и именно это спрашивают на собеседованиях.
•	Результат — критерий приёмки дня: что можно показать/пощупать вечером. Не достигается — день не закрыт, хвост переносится в резерв (дни 37, 44, 51, 56–57, 67), план НЕ сдвигается.
Ежедневный ритуал выхода (3 минуты): коммит (даже WIP) + строка в NEXT.md «следующий конкретный шаг». Возвращение к проекту через 3 дня занимает 30 секунд.
Сквозные фоновые треки (идут ежедневно, не отдельные дни)
•	LeetCode: месяц 1 — 2 easy/день после дня 14; месяцы 2–3 — 2/день (месяц 2: массивы, хеш-таблицы, два указателя, стек, строки; месяц 3: medium — строки, стек/очередь, бинарный поиск, простые графы). Регламент: 20 мин сам → разбор → переписать с нуля → коммит с оценкой сложности. Публичный репозиторий leetcode, ориентир — список Blind 75. К дню 90 — ~100 задач.
•	Exercism (трек Go): по 5 задач в облегчённые дни (7, 14, 21, 28, 51, 67).
•	Рассылка откликов: с дня 30 — 10–15/день (hh.ru, Хабр Карьера, Telegram-каналы), учёт в docs/applications.md (дата/компания/статус).

Окружение и инструменты
Хост — Windows 10/11 x64. Ядро (чистый Go) и Windows-бэкенд разрабатываются и тестируются на хосте нативно — это целевая платформа продукта. Все зависимости — чистый Go (включая modernc.org/sqlite), поэтому кросс-компиляция GOOS=linux go build работает с Windows без дополнительного тулчейна.
Три окружения:
1.	Хост (Windows): повседневная разработка, unit-тесты (mock-бэкенд), read-only операции Windows-бэкенда (списки дисков/шар), веб-панель, git, CI-проверки локально.
2.	ВМ Windows 11 — «полигон»: ВСЕ опасные эксперименты: разметка дисков (DeviceIoControl/Resize-Partition), установка/удаление службы, MSI-апгрейды, ACL-эксперименты, penetration-прогоны. Hyper-V (Gen2, включить vTPM 2.0 — иначе установщик Win11 откажется) или VirtualBox/VMware Workstation. 4+ ГБ RAM, 60+ ГБ диск, второй виртуальный диск (VHDX) — специально для экспериментов с разметкой. Лицензия Windows для разработки не нужна (неактивированная работает с ограничениями на персонализацию). Snapshot перед каждым опасным экспериментом — обязательно.
3.	ВМ Ubuntu 22.04/24.04 (с дня 61): Linux-бэкенд (LVM, Samba). В той же Hyper-V/VirtualBox. Docker Desktop (WSL2) на хосте — вспомогательно для контейнерного варианта (день 66); LVM в контейнере не поднимать — нестабильно из-за device-mapper/loop.
Сеть и доступ к ВМ:
•	VirtualBox: host-only адаптер — стабильный IP вида 192.168.56.x (рекомендуется). Hyper-V: Default Switch — NAT, IP вида 172.x.x.x, может меняться после ребута хоста — каждое утро проверять ipconfig в ВМ и обновлять запись в docs/notes.md.
•	Проверка SMB-доступа к шарами ВМ — с хоста: net use \\192.168.56.10\media /user:TestUser пароль, просмотр — net use, содержимое — dir Z:\.
•	Сброс кэша SMB-сессий на хосте перед повторной проверкой прав (Windows кэширует подключения и Kerberos-билеты): net use * /delete /y + klist purge.
•	Перенос файлов хост↔ВМ: общий каталог (VirtualBox Shared Folders / Hyper-V) или просто git (клонировать репозиторий в ВМ) — второй путь предпочтительнее, заодно тренировка.
Инструменты хоста (установить в день 1): Go ≥ 1.22 (нужен паттерн-роутинг net/http; проверить go version), Git, VS Code + расширение Go (согласиться на установку gopls/dlv), golangci-lint, DB Browser for SQLite, mkcert (для локальных TLS-тестов), hey (go install github.com/rakyll/hey@latest — понадобится в день 50).
Целевая архитектура бинарников: windows/amd64 (основная), linux/amd64 (с дня 62), windows/arm64 и linux/arm64 — опционально в CI. Все артефакты собираются в GitHub Actions.
Если есть машина с macOS (не требуется планом): бэкенд darwin на diskutil — приятное расширение в BACKLOG.md, архитектура это позволяет без изменений ядра.

Главное правило всех 90 дней (правило слоёв): internal/core и internal/api импортируют только интерфейсы из backend.go. Ни одного syscall, wmi, netapi, unsafe вне internal/backend/windows (и os/exec — только внутри бэкендов). Это и есть «главная фишка» проекта: на собеседовании ты объясняешь, ПОЧЕМУ так, а не «я вызывал API». Проверка — grep-ом в дни 14, 58, 73.
Второе правило: FileService работает поверх обычной файловой системы (os/path/filepath) и НЕ требует backend-интерфейса — файлы одинаковы на всех ОС. Backend-интерфейсы остаются для дисков/шар/пользователей. Следствие: файловый менеджер заработает на Linux-бэкенде без единой строчки платформенного кода (проверить в день 88).
0.2. Backend-интерфейсы (контракт, определить дословно в день 4)
package backend

import "context"

type Disk struct {
    DeviceID  string // \\.\PHYSICALDRIVE0
    Model     string
    SizeBytes uint64
    FreeBytes uint64
    IsSystem  bool // жёсткая блокировка деструктивных операций
}

type Partition struct {
    DiskID      string
    Label       string
    DriveLetter string // "E:" или mountpoint (Linux)
    SizeBytes   uint64
    FreeBytes   uint64
    FSType      string
}

type ShareSpec struct {
    Name     string
    Path     string
    ReadOnly bool
    Users    []string
}

type SMARTData struct {
    Available        bool
    Model            string
    TempCelsius      int
    ReallocatedSects int
    PendingSects     int
    PoweredOnHours   int
    HealthStatus     string // ok | warn | fail

0.5. Ключевые архитектурные решения (запомнить навсегда)
1.	Служба Windows работает в Session 0 и не может показывать UI. Поэтому: mininas.exe — служба без окон (только HTTP); tray — отдельный процесс в пользовательской сессии, общается со службой исключительно по HTTP. Запускается по логину через Task Scheduler (или ярлык в shell:startup).
2.	Внешний доступ — только через HTTPS. Панель, торчащая в интернет по HTTP, — это утечка пароля и сессии на первом же перехвате. Два поддерживаемых пути: (а) белый IP — проброс порта 443 + сертификат Let's Encrypt (tls.mode: acme); (б) серый IP (NAT провайдера) — Cloudflare Tunnel (tls.mode: tunnel): наружу не открыт ни один порт, туннель сам ходит в Cloudflare, TLS терминируется на краю + сквозной до origin. При tls.mode: off служба слушает только 127.0.0.1/LAN и предупреждает в логе, что внешний доступ запрещён.
3.	2FA обязательна для внешнего доступа. Пароль — единственный фактор, который брутфорсят боты; TOTP (RFC 6238) — дешёвый второй фактор. Конфиг security.require_2fa_for_external: true — при работе через TLS/tunnel логин админа без включённой 2FA запрещён (принудительный мастер настройки).
4.	Localhost по умолчанию. server.addr: 127.0.0.1:8090; выход в LAN — только явным addr: 0.0.0.0 с предупреждением в лог; внешний доступ — только после дня 47 (TLS+2FA).
5.	Долгие операции — только асинхронно. Создание тома/шары занимает секунды-минуты: HTTP-запрос не должен висеть. Паттерн: POST → job(pending) в БД → 202 + job_id → воркер выполняет → клиент поллит GET /api/jobs/{id}. Источник истины — таблица jobs, не канал в памяти.

День 47 — Внешний контур: TLS + 2FA (ключевой день)
Цель дня: панель доступна по HTTPS; логин админа — двухшаговый с TOTP; продукт готов к выходу в интернет.
Теория (что прочитать/посмотреть перед практикой):
•	TLS: как работает рукопожатие, цепочка доверия; Let's Encrypt (letsencrypt.org/docs): HTTP-01 vs DNS-01 challenge, срок жизни сертификата 90 дней, автопродление;
•	альтернатива для «серого» IP (NAT провайдера): Cloudflare Tunnel (developers.cloudflare.com/cloudflare-one/connections/connect-networks) — cloudflared на машине с NAS сам устанавливает исходящее соединение с Cloudflare, наружу не открыт НИ ОДИН порт, TLS терминируется на краю + опционально сквозной до origin; домен (или поддомен) обязателен;
•	TOTP: RFC 6238 — как из секрета и времени получается 6-значный код; библиотека github.com/pquerna/otp (генерация секрета, otpauth:// URI, валидация с окном ±1 шаг);
•	OWASP: зачем 2FA именно для внешнего доступа (пароль брутфорсят боты, TOTP — нет).
Шаги (выполнять по порядку, время указано ориентировочно):
1.	(1.5 ч) TLS в службе: config tls.mode: off | self | acme | tunnel. self — cert/key из конфига (для ВМ и LAN-тестов: mkcert или New-SelfSignedCertificate); acme — автовыпуск Let's Encrypt (golang.org/x/crypto/acme/autocert, кэш сертификатов в ProgramData, нужен домен + доступный 443); tunnel — служба слушает 127.0.0.1:8090, TLS терминирует cloudflared (настройку туннеля документировать в user-guide).
2.	(0.5 ч) HTTP-слушатель при tls.mode != off: только редирект 301 на HTTPS (или вообще отключён). Cookie-сессии: Secure:true автоматически при tls.mode != off (флаг заложен в день 15). HSTS-заголовок (Strict-Transport-Security) при HTTPS.
3.	(1 ч) 2FA: миграция 004_totp.sql; go get github.com/pquerna/otp. POST /api/2fa/setup → генерация секрета (не сохраняется как активный до подтверждения) + otpauth:// URI + QR в виде SVG прямо в панели (библиотека умеет генерировать картинку; сканировать камерой телефона — Google Authenticator/Authy/1Password).
4.	(1 ч) POST /api/2fa/enable {code} → валидация кода (окно ±1 шаг) → totp_enabled=1 + генерация 8 backup-кодов (bcrypt-хеши в backup_codes, показать пользователю ОДИН раз, скачать .txt). POST /api/2fa/disable {code|backup_code} → выключение только с подтверждением.
5.	(1.5 ч) Двухшаговый логин: POST /api/login (пароль) → если totp_enabled → ответ {second_factor: "totp"} + временная сессия-«полуфабрикат» (отдельная таблица/поле pending, TTL 2 мин, доступа к API нет) → POST /api/login/2fa {code} → полная сессия; ротация токена; rate limit на оба шага.
6.	(0.5 ч) security.require_2fa_for_external: true → при tls.mode != off админ без включённой 2FA видит принудительный мастер настройки при логине (не пускает в панель, пока не включит). CLI-команда mininas user disable-2fa <name> (локально, от админа машины) — спасение при потере телефона.
7.	(1 ч) Страница «Безопасность» в панели: статус TLS, 2FA вкл/выкл, активные сессии (список + «завершить все»), backup-коды.
8.	(1 ч) Тесты: TOTP-валидация (с фиксированным временем), двухшаговый логин, backup-код, редирект на HTTPS, Secure-cookie, «полуфабрикат» не пускает на /api/*. Обновить threat-model.md. Коммит.
Камни (грабли, на которые наступают все — воспроизвести руками хотя бы раз):
•	часы клиента и сервера — TOTP чувствителен к дрейфу: окно ±1 шаг (30 с) обязательно; в ВМ время может уезжать после сна — проверить;
•	autocert в ВМ без реального домена не сработает — для тестов self-signed (mkcert добавляет корень в доверенные — браузер не ругается);
•	backup-коды хранить хешами, не plaintext; показывать один раз;
•	«полуфабрикат» сессии между шагами логина — НЕ полноценная сессия: middleware requireAuth его не принимает, иначе 2FA бессмысленна;
•	Cloudflare Tunnel: X-Forwarded-For/CF-Connecting-IP — доверять заголовкам можно ТОЛЬКО когда слушаешь 127.0.0.1 и туннель единственный источник (иначе подделка IP для обхода rate limit);
•	pprof-порт (день 50) и /api/health без авторизации — при внешнем доступе не должны раскрывать детали (проверить).
Результат дня (критерий приёмки): панель доступна по HTTPS (self-signed в ВМ), логин админа — с TOTP-кодом, backup-коды выданы, threat-model обновлён. Это день, когда MiniNAS перестал быть LAN-игрушкой.
